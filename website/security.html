Security

Security model

SolGate is designed to verify eligibility without requiring custody of user funds or private keys.

Wallet ownership

Wallet control is verified using an off-chain signed message with a server-generated nonce. No SOL transfer is required.

On-chain checks

Token and NFT eligibility is derived from on-chain data and can be re-checked or frozen into a campaign snapshot.

Identity uniqueness

Social identities and wallets can be de-duplicated at the storage layer to reduce duplicate entries and race conditions.

Security controls

AreaApproach
Wallet authenticationNonce-based signed messages and Ed25519 verification.
Token amountsRaw integer balances and BigInt instead of floating-point UI amounts.
OAuth redirectsReturn origins restricted to explicitly allowed application origins.
Signatures / MACsTiming-safe comparison where applicable.
Rate limitingProxy trust is explicit so client IP controls cannot be bypassed through arbitrary forwarded headers.
WebhooksHMAC-signed events and SSRF protections for outbound destinations.
Eligibility privacyPublic eligibility responses expose only the information required by the integration.

What SolGate never needs

Seed phrase
Private key
Recovery phrase
Custody of user funds

Deployment responsibility

Because SolGate is self-hosted, operators are responsible for infrastructure security, secrets, database access, OAuth credentials, RPC reliability, backups, HTTPS and production monitoring.

Alpha status: SolGate has not yet undergone an independent third-party security audit and has not yet been validated in a production mint. Do not treat this documentation as an audit or guarantee of security.
